# OpenClaw, 배포, AI 생성, 프론트 레이아웃, 인증/회원 트러블슈팅 정리

이 문서는 실제 서비스 운영 중 발생했던 문제를 `OpenClaw/배포`, `AI 생성`, `프론트 레이아웃`, `인증/회원` 네 영역으로 나누어 정리한 문서다. 각 항목은 문제 원인, 확인 방법, 적용한 수정, 결과를 중심으로 기록한다.

## 1. OpenClaw/배포

### 1-1. 운영 환경에서 OpenClaw 호출이 405 Invalid HTTP method로 실패

#### 문제
로컬에서는 정상 동작하던 OpenClaw 호출이 시놀로지 운영 환경에서만 `405 Invalid HTTP method`로 실패했다. 같은 엔드포인트를 `curl`로 호출하면 성공했지만, Java 백엔드에서 호출할 때만 문제가 발생했다.

#### 원인
Java `HttpClient`가 운영 환경에서 `HTTP/2` 협상이나 `Expect: 100-continue` 같은 추가 동작을 수행하면서, OpenClaw 앞단에서 요청이 비정상적으로 해석됐다. 즉 URL 문제보다는 Java 클라이언트의 요청 방식 차이였다.

#### 조치
OpenClaw 호출용 Java HTTP 클라이언트를 다음 기준으로 통일했다.

- `HTTP/1.1` 고정
- `Accept: application/json` 명시
- `Expect: 100-continue` 비활성화

#### 결과
운영 환경에서도 OpenClaw 호출이 `curl`과 동일한 수준으로 단순화되어 `405 Invalid HTTP method` 문제가 해결됐다.

### 1-2. Synology 내부에서 OpenClaw를 Tailscale 주소로 호출할 때 불안정

#### 문제
브라우저에서는 Tailscale HTTPS 주소로 OpenClaw 접속이 가능했지만, 시놀로지 내부 Docker 컨테이너에서 같은 주소로 호출할 때 DNS 해석이나 내부 프록시 경로 때문에 실패하거나 지연되는 문제가 발생했다.

#### 원인
컨테이너 내부에서 `https://next.tail...` 같은 Tailscale 공개 주소를 다시 타는 구조는 불필요하게 한 번 더 우회하는 경로였다. 운영 환경에서는 내부 서비스 간 호출은 외부용 경로가 아니라 내부망 직통 경로를 써야 했다.

#### 조치
백엔드에서 OpenClaw를 호출할 때 외부 Tailscale 주소 대신 NAS 내부망 주소를 사용하도록 변경했다.

예시:
- `http://192.168.50.94:18793`
- `http://192.168.50.94:18993`

#### 결과
백엔드 컨테이너에서 OpenClaw로 가는 경로가 단순해졌고, 내부 호출 안정성이 높아졌다.

### 1-3. prod에서 Postgres 대신 H2로 붙는 문제

#### 문제
운영용 Docker Compose에는 Postgres가 정의되어 있었지만, 실제 백엔드는 H2 embedded DB로 연결되고 있었다.

#### 원인
`docker-compose.prod.yml`은 `DATABASE_URL`, `DATABASE_USERNAME`, `DATABASE_PASSWORD`를 컨테이너에 넣고 있었지만, Spring Boot는 이 키 이름만으로 datasource를 자동 구성하지 않았다. `application-prod.yml`에 `spring.datasource.*` 매핑이 없었기 때문에 H2로 fallback됐다.

#### 조치
`application-prod.yml`에 아래 매핑을 추가했다.

- `spring.datasource.url: ${DATABASE_URL}`
- `spring.datasource.username: ${DATABASE_USERNAME}`
- `spring.datasource.password: ${DATABASE_PASSWORD}`

#### 결과
운영 백엔드가 실제로 Postgres에 연결되었고, H2 fallback 문제를 제거했다.

### 1-4. OpenClaw 1/2/3 구조 정리

#### 사실관계
OpenClaw 1, 2, 3은 코드 자체가 따로 설치된 인스턴스가 아니라, 같은 `openclaw:local` 이미지를 공유한다. 서로 다른 것은 아래 두 가지다.

- `openclaw.json` 등 인스턴스별 설정
- `/volume1/docker/openclaw_X/data` 아래 상태/세션/업로드 데이터

즉 코드 패치는 공통으로 적용되고, 동작 차이는 주로 모델/provider 설정과 세션/데이터에서 발생했다.

## 2. AI 생성

### 2-1. 세 가지 모델 경로 중 두 개에서 이미지 입력 기대 형식이 달랐던 문제

#### 문제
OpenClaw를 통해 세 가지 모델 경로를 사용했다.

- `openclaw1`: `openai-codex/gpt-5.3-codex`
- `openclaw2`: `google-gemini-cli/gemini-3-pro-preview`
- `openclaw3`: Ollama 일반 모델 + 비전 모델 조합

이 중 `openclaw2`, `openclaw3`는 1번과 같은 이미지 요청 형식을 그대로 받지 못해 응답이 불안정하거나 실패했다.

#### 기대 형식을 확인한 방법
기대 형식은 추정하지 않고 직접 비교했다.

1. `/v1/files` 업로드가 세 인스턴스 모두 정상인지 확인
2. `/v1/chat/completions`, `/v1/responses`를 각각 직접 호출
3. 응답 코드와 에러 메시지를 비교
4. OpenClaw 서버 로그와 처리 코드 경로를 함께 확인

이 과정을 통해 이미지 분석은 다음 공통 흐름으로 맞추는 것이 가장 안정적이라는 결론을 냈다.

- 이미지 업로드: `/v1/files`
- 분석 요청: `/v1/responses`
- 이미지 참조: `input_image.source.type = "file_id"`

#### 결과
각 모델별 차이를 외부 API 계약이 아니라 내부 변환 레이어 문제로 좁힐 수 있었고, 공통 입력 규격을 정리할 수 있었다.

---

### 2-2. 이미지 참조 문자열이 형식마다 달라 잘못된 이미지를 읽는 문제

#### 문제
백엔드로 들어오는 이미지 참조 형식이 여러 가지였다.

- `/uploads/...`
- `uploads/...`
- `http://localhost:3000/uploads/...`
- 순수 파일명
- DB에 저장된 object key

이 차이 때문에 어떤 요청은 같은 이미지를 가리키고도 백엔드가 다른 파일로 해석하거나, 아예 `지원하지 않는 이미지 참조 형식`으로 처리했다.

#### 조치
이미지 참조 정규화 레이어를 구현했다.

- 상대경로는 절대 업로드 경로로 치환
- URL은 파일명을 추출해 로컬 업로드 디렉터리와 매핑
- 순수 파일명도 허용
- 최종적으로 하나의 실제 파일 경로로 수렴

#### 결과
프론트에서 어떤 형태로 이미지가 전달되더라도, 백엔드는 일관된 파일 경로와 일관된 OpenClaw `file_id`를 기준으로 처리할 수 있게 됐다.

---

### 2-3. 이전 이미지 분석 결과가 다음 요청에 섞이는 문제

#### 문제
이미지 업로드와 분석은 정상인데도, 실제 응답에 이전 이미지 설명이 섞이거나 과거 실패 문맥이 이어지는 문제가 있었다.

#### 원인
OpenClaw 요청이 같은 세션으로 계속 처리되면서 이전 문맥이 다음 요청에 재사용되고 있었다. 특히 여러 사용자가 동시에 요청하거나, 한 사용자가 연달아 다른 이미지를 테스트할 때 증상이 더 심해졌다.

#### 조치
분석 요청마다 고유 `SessionKey`를 부여해 요청 단위로 세션을 격리했다.

#### 이유
- 이미지 분석은 이전 문맥을 거의 이어받을 필요가 없음
- 요청마다 독립 세션이 더 안전함
- 여러 사용자의 요청이 섞이는 것을 방지해야 함

#### 결과
이전 이미지 설명이나 실패 문맥이 다음 요청에 섞이는 빈도를 크게 줄였다.

---

### 2-4. OpenClaw 3번의 비전/일반 모델 자원 사용 최적화

#### 문제
3번은 Ollama 기반 비전 모델과 일반 모델을 같이 쓰는 구조였는데, 이미지 분석이 끝난 뒤에도 두 모델이 동시에 오래 유지되는 것처럼 보여 응답 속도와 자원 사용량에 부담이 있었다.

#### 조치
3번을 순차 처리 구조로 재설계했다.

1. 비전 모델이 이미지를 먼저 해석
2. 일반 모델이 비전 결과 텍스트만 받아 최종 JSON 생성
3. 비전 단계 종료 후 unload 시도
4. 일반 단계 종료 후 일반 모델 unload 시도

#### 결과
이미지 처리와 최종 생성 역할이 분리되어 자원 사용이 명확해졌고, 모델 간 중복 작업을 줄였다.

---

### 2-5. 프롬프트 설계 정리

#### 문제
AI 응답이 지나치게 길거나, 배경보다 감상 표현이 많아 실제 디자인에 필요한 정보보다 문장형 수사가 앞서는 경우가 있었다.

#### 조치
프롬프트를 다음 기준으로 조정했다.

- 인물 행동과 배경 설명 우선
- 세부 감정 해석 과다 제한
- 대표 컬러는 1개만 설명
- `analysisSummary`는 더 짧고 구체적으로
- `colorStrategy`는 더 짧고 간결하게
- `congratulatoryMessage`는 1~2문장 위주로 제한

#### 결과
디자인 의사결정에 필요한 정보 위주로 답이 정리되었고, 결과 문체도 과도하게 늘어지지 않게 되었다.

## 3. 프론트 레이아웃

### 3-1. `/builder`와 `/admin/skins` 미리보기 레이아웃이 다르게 보이던 문제

#### 문제
같은 `InvitationView`를 쓰는데도 `builder`와 `admin/skins`에서 레이아웃이 다르게 보였다. 특히 일반 박스(`standard`)와 전체 배경(`full`)의 사진 비율, 텍스트 위치, 웹 미리보기 폭이 서로 달랐다.

#### 원인
미리보기 렌더 분기가 페이지마다 달랐다.

- `isPreview`
- `compactPreview`
- `previewUseLivePhotoLayout`
- `imageStyle`
- `mainPhotoFit`

이 조합이 서로 다르게 적용되면서 같은 컴포넌트가 다른 레이아웃으로 보였다.

#### 조치
- `standard`와 `full`을 같은 방식으로 처리하지 않고 분리
- `/admin/skins` 웹 미리보기만 별도 조정
- 메인페이지와 builder, skins preview의 역할을 분리해 필요한 경우에만 같은 렌더 경로를 타게 수정

#### 결과
원하지 않는 전역 레이아웃 영향 없이, 특정 미리보기 화면만 조정할 수 있게 됐다.

---

### 3-2. 전체 텍스트 배율이 히어로 레이아웃까지 흔들던 문제

#### 문제
전체 텍스트 배율 조정이 `save the date`, 날짜, gallery, location 같은 일반 텍스트만이 아니라 히어로 전체 레이아웃과 사진 배치까지 흔들고 있었다.

#### 원인
히어로 내부의 줄바꿈/레이아웃 계산이 전역 `textScale`에 의존하고 있었다.

#### 조치
히어로 레이아웃 계산에서 `textScale` 의존성을 제거했다.

#### 결과
전체 텍스트 배율은 일반 텍스트에만 적용되고, 히어로 레이아웃과 사진 영역은 고정된 비율을 유지하게 됐다.

---

### 3-3. 저장된 스킨 텍스트 색보다 자동 흰색/검정이 우선되던 문제

#### 문제
full 이미지 히어로에서 DB에 저장된 `titleColor`, `nameColor`, `dateColor` 등이 있어도, 이미지 밝기에 따라 자동으로 흰색 또는 검정이 덮어씌워지는 문제가 있었다.

#### 원인
저장 시점 또는 렌더 시점에 `heroTextColorMode`가 `auto`로 남아 있으면 자동 대비 로직이 저장된 색을 덮어쓰고 있었다.

#### 조치
- 저장된 hero 텍스트 색상이 있으면 `heroTextColorMode`를 `custom`으로 보정
- 렌더 단계에서도 DB에 명시 색상이 있으면 자동 흰색/검정 강제를 막도록 수정

#### 결과
저장된 스킨의 DB 색상값이 실제 렌더에 우선 적용되도록 정리했다.

---

### 3-4. 메인페이지 스킨 프리뷰가 샘플 이미지에 끌리던 문제

#### 문제
메인페이지 스킨 프리뷰가 실제 저장 이미지보다 샘플 이미지에 더 자주 의존했다.

#### 조치
이미지 우선순위를 정리했다.

1. `displayPhotoUrl`
2. `thumbnail`
3. `mainPhotoUrl`
4. `photoUrl`
5. 샘플 이미지 fallback

#### 결과
실제 저장 이미지가 있으면 그것이 우선 사용되고, 샘플 이미지는 최후 fallback으로만 남았다.

## 4. 인증/회원

### 4-1. 소셜 로그인 시 미가입 계정 처리 불명확

#### 문제
가입하지 않은 계정으로 소셜 로그인을 시도하면, 사용자 입장에서 로그인 실패인지 회원가입 유도인지 애매한 상태가 발생했다.

#### 조치
로그인과 회원가입 의도를 분리했다.

- 로그인 페이지: `mode=login`
- 회원가입 페이지: `mode=signup`

그리고 미가입 계정이 로그인 시도를 하면 명확한 메시지를 반환하도록 수정했다.

- `가입되지 않은 계정입니다. 먼저 회원가입해 주세요.`

#### 결과
소셜 로그인 UX가 명확해졌고, 로그인/회원가입 경계가 분리되었다.

---

### 4-2. `auth/me` 500 오류

#### 문제
인증 상태 확인 API에서 `500`이 발생하는 경우가 있었다.

#### 원인
`Authentication.getPrincipal()`을 무조건 문자열로 캐스팅하는 코드가 있어, principal 타입이 다를 경우 예외가 발생했다.

#### 조치
`authentication.getName()`을 우선 사용하고, 필요 시 fallback으로 처리하도록 수정했다.

#### 결과
인증 상태 조회 API의 안정성이 개선되었다.

---

### 4-3. 관리자 회원 삭제 API 500

#### 문제
관리자 회원 삭제 API가 특정 사용자 삭제 시 `500`을 반환했다.

#### 원인
`deleteByEmail()` 기반 삭제는 JPA cascade 삭제를 타지 않아, 연관 엔티티가 남아 있을 때 FK 제약으로 실패했다.

#### 조치
- `findByEmail()`로 사용자 엔티티 조회
- `userRepository.delete(user)` 호출로 aggregate 삭제 경로 사용

#### 결과
연관 엔티티까지 함께 정리되며 관리자 회원 삭제 API가 정상 동작하게 되었다.

---

## 정리

이번 트러블슈팅에서 가장 중요한 기준은 다음 네 가지였다.

1. OpenClaw는 코드보다도 `payload 규격`, `세션`, `네트워크 경로`가 중요하다.
2. 이미지 기반 AI 생성은 파일 업로드보다 `참조 문자열 정규화`와 `세션 분리`가 더 중요할 수 있다.
3. 프론트 레이아웃은 공통 컴포넌트를 쓰더라도 preview 분기가 다르면 전혀 다른 결과가 나온다.
4. 운영 환경 장애는 `로컬에서는 된다`로 끝내지 말고, 실제 `prod 네트워크`, `prod datasource`, `prod 요청 방식` 기준으로 확인해야 한다.
