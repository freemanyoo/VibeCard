# VibeCard Portfolio Outline

## 1. 프로젝트 한 줄 소개

VibeCard는 사용자가 모바일 청첩장을 직접 제작하고 공유할 수 있고, 하객 응답과 방명록을 수집하며, AI를 이용해 디자인 초안을 보조 생성할 수 있는 웹 서비스입니다.

## 2. 포트폴리오 기준 재정의

포트폴리오 설명은 아래 4개 관점으로 나눕니다.

1. 사용자 흐름
2. AI 기능
3. 관리자 흐름
4. 설계 / 구조

이 기준을 쓰는 이유는 다음과 같습니다.

- 사용자 기능과 관리자 기능이 섞이면 서비스 흐름이 흐려집니다.
- 스킨 시스템처럼 사용자와 관리자 모두 걸치는 기능은 설계 관점으로 빼야 중복이 줄어듭니다.
- 포트폴리오는 기능 목록이 아니라 "서비스를 어떻게 만들었는지" 보여주는 문서여야 합니다.

## 4. 사용자 흐름

### 4-1. 회원가입 / 로그인

- 이메일 회원가입과 Google, Naver, Kakao 소셜 로그인을 함께 지원하도록 인증 흐름을 구성했습니다.
- JWT + Refresh Token 구조로 로그인 상태를 유지하도록 구현했습니다.
- 로그인 이후 곧바로 대시보드로 이어지도록 구성해 청첩장 작성 흐름이 끊기지 않게 했습니다.

추천 이미지:
- 로그인 페이지 전체 화면
- 이메일 로그인 + 소셜 로그인 버튼이 함께 보이는 화면
- 로그인 후 대시보드 진입 화면

### 4-2. 청첩장 생성 및 편집

- 사용자가 새 청첩장을 만들면 slug 기반 공개 URL이 생성되고, 바로 편집 화면에서 내용을 수정할 수 있도록 구현했습니다.
- 신랑/신부 정보, 예식 일시, 장소, 초대 문구, 계좌정보, 갤러리 이미지 등을 한 화면에서 관리할 수 있게 구성했습니다.
- 사용자는 청첩장 생성 및 편집 과정에서 미니 스킨 미리보기를 보며 디자인을 선택할 수 있습니다.
- 수정 결과가 즉시 미리보기에 반영되도록 만들어 실제 공개 화면을 보면서 편집할 수 있게 했습니다.

추천 이미지:
- 생성 직후 편집기로 이동한 화면
- 미니 스킨 미리보기를 보고 디자인을 선택하는 편집 화면
- 대표 이미지나 문구 수정 결과가 반영된 편집 화면

### 4-3. 이미지 업로드 및 미디어 관리

- 청첩장 대표 이미지와 갤러리 이미지를 업로드할 수 있도록 구현했습니다.
- 원본, 썸네일, 분석용 이미지 메타데이터를 분리해 이후 AI 기능과 연결할 수 있게 설계했습니다.
- 편집기 미리보기와 실제 공개 페이지가 같은 이미지 경로를 사용하도록 정리해, 저장 후에도 동일한 대표 이미지가 보이게 했습니다.

추천 이미지:
- 대표 이미지 업로드 UI
- 갤러리 이미지 업로드 화면
- 업로드 결과가 청첩장에 반영된 화면

### 4-4. AI 이미지 기반 / 명령어 기반 디자인 생성

- 사용자가 프롬프트를 입력하거나 대표 이미지를 업로드하면 AI가 청첩장 디자인 초안을 생성하도록 구현했습니다.
- 이미지 기반 생성과 명령어 기반 생성을 분리해 각각 다른 입력 흐름으로 처리할 수 있게 구성했습니다.
- 생성 결과는 단순 텍스트가 아니라 실제 편집 가능한 설정값으로 연결되도록 설계했습니다.

추천 이미지:
- AI 생성 모달
- 프롬프트 입력 화면
- 이미지 기반 생성 화면
- 생성 결과 반영 전/후 비교 화면

### 4-5. 공개 청첩장 및 하객 상호작용

- 하객이 실제로 접속하는 모바일 청첩장 페이지를 구현했습니다.
- 장소 정보, 길찾기, 계좌 보기, 참석 여부 제출, 방명록 작성 등 예식 안내에 필요한 기능을 포함했습니다.
- 공개 페이지에서 입력된 참석 응답과 메시지가 청첩장 단위로 연결되도록 설계했습니다.

추천 이미지:
- 실제 청첩장 공개 페이지 전체 화면
- 장소 / 계좌 / 참석 여부 섹션이 보이는 화면
- 방명록 또는 RSVP 입력 화면

## 5. 관리자 흐름

### 5-1. AI 스킨 생성

- 관리자가 프롬프트를 입력하면 AI가 새로운 스킨 초안을 생성하도록 구현했습니다.
- 생성 결과는 단순 설명이 아니라 실제 스킨 설정값과 초안 데이터로 이어지도록 구성했습니다.
- 스킨 제작 시간을 줄이면서도, 이후 관리자 화면에서 직접 수정할 수 있도록 운영 흐름에 연결했습니다.

추천 이미지:
- 관리자 AI 스킨 생성 화면
- 프롬프트 입력 후 생성 결과가 반영된 화면

### 5-2. 관리자 스킨 관리

- 관리자는 별도의 스킨 디자인 관리 화면에서 스킨을 생성, 수정, 삭제할 수 있도록 구성했습니다.
- 사용자 작성 흐름과 분리된 운영 화면에서 스킨을 관리하도록 설계했습니다.

추천 이미지:
- 관리자 스킨 관리 페이지
- 스킨 생성 또는 수정 화면

### 5-3. 운영 로그 및 권한 관리

- 악성 프롬프트 요청이나 AI 오용 시도를 별도 로그로 남겨 운영 중 모니터링할 수 있게 했습니다.
- 관리자 전용 화면은 일반 사용자 기능과 분리하고 권한 기반 접근 제어를 적용했습니다.

추천 이미지:
- AI 차단 로그 화면
- 관리자 전용 운영 화면

## 6. 설계 / 구조

### 6-1. 스킨 시스템 구조

- 청첩장을 스킨 단위로 분리해 여러 디자인을 재사용할 수 있도록 구성했습니다.
- 스킨별 설정값(config) 기반으로 색상, 텍스트, 이미지 스타일이 적용되도록 설계했습니다.
- 같은 청첩장 데이터라도 스킨을 바꾸면 다른 결과가 나오도록 렌더링 구조를 분리했습니다.

추천 이미지:
- 서로 다른 스킨이 적용된 청첩장 결과 비교
- 같은 청첩장 데이터에 스킨만 바꿨을 때 달라지는 미리보기 비교

### 6-2. 데이터 구조

- 사용자 중심으로 청첩장, 이미지, AI 생성 기록이 연결되는 구조입니다.
- 청첩장 하나에 계좌정보, 참석 응답, 방명록이 종속되는 구조로 설계했습니다.
- 현재는 관계 객체와 문자열 id 컬럼이 함께 있는 과도기 구조이며, FK 기반 구조로 정리 중입니다.

추천 이미지:
- ERD

### 6-3. 유스케이스

- 사용자 흐름은 인증 → 청첩장 생성/편집 → 공개 → 하객 응답 순으로 이어집니다.
- AI 기능은 편집 흐름을 보조하는 기능으로 붙였고, 관리자 기능은 별도 운영 흐름으로 분리했습니다.

추천 이미지:
- Use Case Diagram

## 7. 기술적 고민과 해결

### 7-1. 인증 구조

- 이메일 로그인과 소셜 로그인을 함께 지원하면서 세션 유지 방식을 통일해야 했습니다.
- JWT + Refresh Token 구조를 도입해 인증 흐름을 단순화했습니다.

### 7-2. 편집기와 실제 공개 화면의 일관성

- 편집기 미리보기와 실제 공개 청첩장이 다르게 보이는 문제가 있었습니다.
- 대표 이미지, 텍스트, 스킨 설정값 반영 구조를 정리해 두 화면 간 차이를 줄였습니다.

### 7-3. 이미지 저장 구조

- 대표 이미지, 썸네일, 분석용 이미지가 각각 다른 목적을 가지므로 메타데이터를 분리했습니다.
- 이후 MinIO나 외부 스토리지로 이전할 수 있도록 확장 가능한 구조를 고려했습니다.

### 7-4. AI 연동

- 프롬프트 기반 생성과 이미지 기반 생성을 분리해서 설계했습니다.
- 생성 결과를 단순 텍스트가 아니라 실제 편집 가능한 설정값으로 연결하도록 설계했습니다.

## 9. 이미지 선정 기준

좋은 이미지:

- 기능이 한눈에 보이는 화면
- 입력과 결과가 함께 보이는 화면
- 전후 비교가 가능한 화면
- 실제 사용자 가치가 드러나는 화면

피해야 할 이미지:

- 설정 항목만 잔뜩 보이는 화면
- 차이가 거의 없는 비슷한 화면 여러 장
- 오류 메시지 중심 화면
- 너무 작은 일부 영역만 캡처한 화면
