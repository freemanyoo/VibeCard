# OpenClaw AI 이미지 생성 트러블슈팅 면접 답변

AI 청첩장 생성 기능을 구현하면서 OpenClaw를 통해 세 가지 모델 경로를 연동한 경험이 있습니다. 1번은 `openai-codex/gpt-5.3-codex`, 2번은 `google-gemini-cli/gemini-3-pro-preview`, 3번은 로컬 Ollama 기반 일반 모델과 비전 모델 조합이었는데, 이 중 2번과 3번은 처음에 1번과 같은 요청 형식을 그대로 넣었을 때 안정적으로 동작하지 않았습니다. 핵심 원인은 모델별 기대 형식이 완전히 같지 않았던 점이었고, 이 차이는 추측이 아니라 실제 요청과 로그를 비교하면서 확인했습니다.

먼저 `/v1/files` 업로드가 세 인스턴스 모두에서 정상적으로 동작하는지 확인한 뒤, `/v1/chat/completions`와 `/v1/responses`에 각각 직접 요청을 보내 응답 코드와 메시지를 비교했습니다. 그 과정에서 1번은 기존 요청이 일부 수용됐지만, 2번과 3번은 같은 payload에서 응답이 불안정하거나 실패했고, OpenClaw 서버 로그와 코드 경로를 함께 따라가 보니 이미지 분석 경로는 `/v1/files`로 파일을 먼저 올린 뒤 `/v1/responses`에서 `input_image.source.type = "file_id"` 형식으로 전달하는 방식이 가장 일관된 공통 규격이라는 것을 확인할 수 있었습니다. 그래서 이미지 분석 요청 규격을 이 구조로 통일했습니다.

이미지 참조 문자열도 중요한 문제였습니다. 실제 운영 과정에서는 `/uploads/...`, `uploads/...`, `http://localhost:3000/uploads/...`, 순수 파일명, DB에 저장된 object key 같은 값이 섞여 들어왔고, 이 차이 때문에 백엔드가 동일한 이미지를 전혀 다른 파일로 해석하거나 아예 "지원하지 않는 이미지 참조 형식"으로 처리하는 문제가 발생했습니다. 이 부분은 입력 문자열을 정규화하는 레이어를 두고 해결했습니다. 상대경로는 절대 업로드 경로로 치환하고, URL은 파일명만 추출해 로컬 업로드 디렉터리와 매핑하며, 순수 파일명도 허용해 최종적으로는 하나의 실제 파일 경로로 수렴하도록 만들었습니다. 이렇게 해서 프론트에서 어떤 형식으로 전달되더라도 백엔드는 동일한 로컬 이미지와 동일한 OpenClaw `file_id`를 기준으로 처리할 수 있게 했습니다.

세션 키를 부여한 이유는 문맥 오염을 막기 위해서였습니다. OpenClaw 요청이 동일 세션으로 반복되면 이전 요청에서 사용한 이미지 설명이나 실패 문맥이 다음 요청에 섞일 수 있었고, 실제로 이전 이미지 분석 결과가 다음 요청에 재사용되는 현상이 발생했습니다. 특히 여러 사용자가 동시에 요청하거나, 한 사용자가 연속으로 다른 이미지를 테스트할 때 이 문제가 더 두드러졌습니다. 그래서 분석 요청마다 고유 `SessionKey`를 생성해 전달했고, 요청 단위 컨텍스트를 분리해 이전 이미지 정보가 다음 요청에 섞이지 않도록 했습니다.

운영 환경에서는 Java HTTP 클라이언트를 `HTTP/1.1`로 고정하고 내부망 주소를 사용하도록 바꾼 것도 중요한 해결 포인트였습니다. 실제로 로컬에서는 정상 동작하던 요청이 운영 환경에서만 `405 Invalid HTTP method`로 실패했는데, 같은 엔드포인트를 `curl`로 호출하면 성공했습니다. 이 차이를 비교해 보니 Java 클라이언트가 `HTTP/2` 협상이나 `Expect: 100-continue` 같은 추가 동작을 시도하면서 OpenClaw 앞단에서 요청이 잘못 해석되는 문제가 있었습니다. 그래서 요청 방식을 `curl`에 가깝게 단순화하기 위해 `HTTP/1.1`로 고정하고 `Accept: application/json`을 명시하며 `Expect: 100-continue`를 비활성화했습니다. 또한 시놀로지 내부 컨테이너에서 OpenClaw를 호출할 때는 Tailscale 공개 주소 대신 `192.168.50.94:18793`, `192.168.50.94:18993` 같은 내부망 주소를 사용하도록 바꿨습니다. 외부용 Tailscale 경로는 브라우저에서는 문제없었지만, 컨테이너 내부에서는 DNS 해석이나 프록시 경로 때문에 불안정할 수 있었기 때문입니다.

결과적으로 요청 포맷, 이미지 참조 방식, 세션, 네트워크 경로를 모두 통제하면서 이미지 기반 AI 생성 흐름을 운영 환경에서도 안정적으로 동작하도록 만들었습니다. 이 경험을 통해 단순히 모델 호출 코드만 보는 것이 아니라, API 규격, 컨텍스트 격리, 배포 환경 네트워크 차이까지 함께 봐야 실제 서비스 품질을 끌어올릴 수 있다는 점을 배웠습니다.

## Synology Docker 프록시 트러블슈팅 면접 답변

또 다른 트러블슈팅 경험으로는 Synology Docker 환경에서 프론트엔드와 백엔드를 분리 배포했을 때, 브라우저에서 `/api` 요청이 계속 `504 Gateway Timeout`으로 실패했던 문제가 있었습니다. 당시 구조는 React 정적 파일을 Nginx 컨테이너가 서빙하고, Spring Boot 백엔드는 별도 컨테이너로 띄운 뒤 호스트 포트 `8086`을 통해 공개하는 방식이었습니다. 처음에는 프론트 Nginx가 `host.docker.internal:8086`으로 백엔드를 프록시하도록 설정했는데, 겉으로 보기에는 호스트 포트만 열려 있으면 될 것 같았지만 실제 Synology 환경에서는 이 경로가 안정적으로 동작하지 않았습니다. 로그인, 회원가입, 이메일 인증, 이미지 업로드 같은 요청이 전부 동일하게 실패했고, 처음에는 백엔드 비즈니스 로직 문제처럼 보였지만, 기능별로 모두 같은 증상이 난다는 점에서 네트워크 경로 자체를 먼저 의심했습니다.

이 문제는 프론트 컨테이너 내부에서 직접 백엔드 경로를 검증하면서 좁혔습니다. 우선 브라우저 기준으로는 `/api/auth/social/google`이나 `/api/auth/register/send-code`가 모두 `504`를 반환했기 때문에, 백엔드가 실제로 죽어 있는지 먼저 확인했습니다. 백엔드 컨테이너 자체는 살아 있었고, 호스트에서 `curl http://127.0.0.1:8086`을 보내면 정상적으로 `401`이나 JSON 에러 응답이 왔습니다. 반면 프론트 Nginx 컨테이너 안에서 `curl http://host.docker.internal:8086`을 보내면 타임아웃이 발생했습니다. 여기서 문제를 "브라우저 -> Nginx" 구간이 아니라 "프론트 컨테이너 -> 백엔드" 구간으로 좁힐 수 있었고, 실제로 프론트 컨테이너는 기본 `bridge` 네트워크에, 백엔드는 `vibecard_default` 네트워크에 올라가 있어 서비스명으로 직접 통신하지 못하는 구조였습니다.

해결은 우회 경로를 유지하는 대신 네트워크 구조를 바로잡는 방향으로 갔습니다. 프론트 Nginx 컨테이너를 백엔드와 동일한 `vibecard_default` 네트워크에 연결하고, 프록시 대상을 `host.docker.internal:8086`에서 `backend:8080`으로 변경했습니다. 이렇게 바꾸면 요청 흐름이 "브라우저 -> 프론트 Nginx -> 같은 Docker 네트워크의 backend 서비스명"으로 단순해지고, 호스트 포트 우회나 Synology 호스트 라우팅에 의존하지 않게 됩니다. 변경 후 프론트 컨테이너 내부에서 `getent hosts backend`와 `curl http://backend:8080`으로 연결을 다시 확인했을 때, 즉시 정상 응답이 왔고, 외부 도메인 기준 `/api` 요청도 더 이상 `504`가 아니라 실제 백엔드 응답 코드인 `400`, `401` 등으로 바뀌었습니다. 이 변화는 프록시 경로가 정상화됐다는 결정적 증거였습니다.

운영 도메인 전환 과정에서 CORS도 같이 정리했습니다. 외부 주소를 `https://vibecard.nextfreemanyoo.myds.me`로 고정한 뒤에도 Google OAuth 요청이 `403`으로 보였는데, 이는 프론트와 백엔드가 같은 도메인 아래에서 통신하더라도 Spring Security의 CORS 허용 목록에 운영 도메인이 빠져 있었기 때문이었습니다. 그래서 보안 설정에 운영 도메인을 추가하고 백엔드를 다시 배포했습니다. 이후 `/api/auth/social/google`은 더 이상 프록시 오류나 CORS 차단이 아니라, 실제 인증 실패 여부를 백엔드 JSON으로 반환하게 되었고, 문제를 네트워크 계층과 인증 계층으로 분리해서 볼 수 있게 됐습니다.

이 경험에서 가장 중요했던 점은, `504`나 `403` 같은 증상을 바로 애플리케이션 로직 문제로 보지 않고 요청이 어느 계층에서 끊기는지 단계별로 확인했다는 점입니다. 브라우저 네트워크 탭, 컨테이너 내부 `curl`, Docker 네트워크 연결 상태, Spring Security 설정을 순서대로 확인하면서 문제를 좁혔고, 결과적으로 Synology 운영 환경에서도 프론트와 백엔드가 안정적으로 통신하는 배포 구조로 정리할 수 있었습니다.

## AI 청첩장 명령어 기반 입력 분리 및 폰트 정책 트러블슈팅 면접 답변

최근에는 AI 청첩장 생성 기능에서 `이미지 기반`과 `명령어 기반`의 경계가 흐려져 있던 문제를 정리한 경험이 있습니다. 기능 의도상 `이미지 기반`은 업로드한 사진을 보고 색감과 분위기를 추론해야 하고, `명령어 기반`은 사용자가 입력한 텍스트 설명만으로 디자인 방향을 만들어야 했습니다. 그런데 실제 코드를 확인해 보니 `명령어 기반` 요청에도 `sourceImageId`, `analysisImageUrl`, `photoUrl` 같은 값이 함께 전달될 수 있는 구조였고, 이 경우 사용자는 텍스트만으로 결과가 나온다고 생각하지만 실제 AI는 이미지 맥락까지 같이 참고하게 되는 상태였습니다. 이 문제는 결과가 미묘하게 흔들린다는 피드백으로 먼저 드러났고, 요청 payload와 서버 로그를 비교하면서 원인을 구체적으로 확인했습니다.

처음에는 프론트엔드 쪽만 수정하면 될 것처럼 보였지만, 실제 서비스에서는 프론트와 백엔드 둘 중 하나만 믿고 가면 다시 동일한 문제가 생길 수 있다고 판단했습니다. 그래서 클라이언트 요청 구조와 서버 처리 로직을 함께 정리하는 방향으로 접근했습니다. 프론트엔드에서는 `명령어 기반` 요청을 보낼 때 이미지 관련 필드를 아예 제거했고, 백엔드에서도 `prompt` 엔드포인트에 들어온 요청은 방어적으로 `null`을 넘겨 이미지 분석 경로를 타지 못하도록 막았습니다. 이렇게 하면 프론트가 다시 잘못된 값을 보내더라도 서버 기준으로는 여전히 텍스트 전용 파이프라인이 유지됩니다. 저는 이런 경우를 단순 버그 수정이 아니라 "클라이언트와 서버 간 계약을 다시 정의하는 작업"으로 봅니다.

같이 드러난 또 다른 문제는 폰트 선택 기준이 불명확하다는 점이었습니다. 기존 `명령어 기반` 흐름에서는 AI가 색상 팔레트와 텍스트 계열 값은 반환해도 `fontFamily`는 필수값이 아니었고, 설령 반환하더라도 서비스에서 허용한 무료 폰트 목록과 다를 수 있었습니다. 이 상태에서는 생성 결과가 스킨 디자인 정책과 어긋나거나, 저장 단계에서 폰트 보정이 일어나 디자인 의도가 달라질 수 있었습니다. 처음에는 프론트에 수동 폰트 선택 UI를 붙여 해결할 수도 있었지만, 기능 요구사항은 "명령어 기반에서는 AI가 폰트까지 결정해야 한다"는 쪽이었기 때문에 그 방식은 적절하지 않았습니다. 그래서 방향을 다시 잡고, 백엔드 프롬프트와 응답 파서를 이용해 AI가 정책 안에서 직접 선택하게 만드는 구조로 바꿨습니다.

구체적으로는 백엔드 `prompt-only` 프롬프트에 `fontFamily`를 필수 응답 값으로 추가하고, 스킨 디자인에서 실제 사용하는 무료 폰트 목록 전체를 명시했습니다. 그리고 응답 파서에서는 이 값을 그대로 저장하지 않고, 허용 목록과 비교해 일치하는 경우만 통과시키고, 표현만 조금 다른 경우에는 정규화해서 매핑하도록 했습니다. 예를 들어 따옴표나 공백 차이로 같은 폰트가 다르게 들어와도 동일한 허용 폰트로 인식하게 만들었습니다. 반대로 목록 밖 값이 오거나 모델이 아예 `fontFamily`를 누락하면, 마지막 안전장치로 기본 무료 폰트를 넣도록 fallback 로직도 추가했습니다. 이렇게 해서 모델 응답 편차가 있더라도 저장 데이터는 항상 정책 안에 머무르게 했습니다.

배포 과정에서도 실제 운영 이슈가 하나 있었습니다. 백엔드 JAR를 교체하고 Docker Compose로 재기동하는 과정에서 처음에는 운영용 `.env.prod`를 명시하지 않아 기본 포트 기준으로 `postgres`가 올라오려 하면서 포트 충돌이 발생했습니다. 이때 컨테이너 상태와 환경파일 경로를 다시 확인해 운영은 `POSTGRES_PORT=5532`, `BACKEND_PORT=8086` 기준이라는 점을 재확인했고, 그 환경파일을 명시해서 다시 배포했습니다. 이후 백엔드 컨테이너가 재생성되면서 IP가 바뀌자 프론트 Nginx가 이전 upstream IP를 바라봐 외부 `/api`가 잠깐 `502`를 반환했는데, 프론트 컨테이너 내부에서 `backend` 서비스명으로는 이미 통신이 된다는 점을 확인한 뒤 `nginx -s reload`로 바로 복구했습니다. 이 과정에서 "애플리케이션은 정상인데 프록시 캐시된 upstream 때문에 외부만 실패할 수 있다"는 점을 다시 확인했습니다.

결과적으로 `명령어 기반`은 이제 실제로 텍스트만으로 AI가 디자인을 생성하고, 폰트도 서비스에서 허용한 무료 목록 안에서 AI가 직접 선택하도록 정리됐습니다. 저는 이 경험을 통해 생성형 AI 기능은 단순히 모델 호출이 성공하는 것만으로 끝나지 않고, 어떤 입력을 허용할지, 어떤 응답만 저장할지, 운영 배포 후 프록시 계층까지 어떻게 안정화할지를 함께 다뤄야 비로소 서비스 품질이 나온다는 점을 배웠습니다.

## 운영 도메인 전환 후 Google OAuth 트러블슈팅 면접 답변

운영 도메인으로 서비스를 전환한 뒤에도 Google 로그인 버튼은 겉으로 보기에는 정상처럼 동작했습니다. 프론트엔드는 Google credential을 받아왔고, 버튼 콜백도 실행되고 있었기 때문에 처음에는 프론트 쪽 구현이 문제없다고 판단하기 쉬웠습니다. 그런데 실제로는 로그인 완료가 되지 않았고, 브라우저 네트워크 탭에서 보면 `/api/auth/social/google` 요청이 `401`, `403`, `504`처럼 상황에 따라 다른 응답을 반환하고 있었습니다. 이 문제는 단일 원인보다는 운영 환경에서 필요한 설정이 여러 군데 나뉘어 빠져 있던 경우였습니다.

먼저 프론트와 백엔드를 분리해서 확인했습니다. 프론트에서는 credential 자체는 정상적으로 수신되고 있었기 때문에, 문제를 "Google SDK 단계"가 아니라 "프론트 이후 백엔드 검증 단계"로 좁혔습니다. 이후 시놀로지 운영 환경의 `.env.prod`와 실제 실행 중인 백엔드 컨테이너 환경변수를 확인해 보니, 로컬 개발 환경에는 값이 있었지만 운영 컨테이너에는 `GOOGLE_CLIENT_ID`가 비어 있었습니다. 즉 프론트는 Google에서 토큰을 받아오더라도, 백엔드가 그 토큰을 검증할 때 기준이 되는 클라이언트 ID가 빠져 있어 인증을 정상 처리할 수 없는 상태였습니다. 여기에 더해 운영 도메인 `https://vibecard.nextfreemanyoo.myds.me`가 Spring Security의 CORS 허용 목록에 포함되어 있지 않아, 프록시 문제를 해결한 뒤에는 같은 요청이 `403`으로 보이기도 했습니다.

해결은 운영 환경 기준으로 인증 설정을 다시 맞추는 방식으로 진행했습니다. 먼저 시놀로지의 운영 환경변수 파일에 실제 `GOOGLE_CLIENT_ID`를 반영하고 백엔드 컨테이너를 재배포했습니다. 그다음 Spring Security CORS 설정에 운영 도메인과 내부 테스트 주소를 추가해, 운영 환경에서도 인증 요청이 정책상 차단되지 않도록 정리했습니다. 이후 프론트에서 받은 Google credential이 백엔드에서 정상적으로 검증되기 시작했고, 최종적으로 운영 도메인에서도 Google 로그인이 완료되는 것을 확인했습니다.

이 경험에서 배운 점은 OAuth 문제를 단순히 "프론트 버튼이 안 된다"거나 "백엔드 API가 실패한다" 수준으로 보면 원인을 놓치기 쉽다는 점입니다. 실제 서비스에서는 Google SDK, 프론트 요청 payload, 운영 환경변수, 백엔드 토큰 검증, 보안 정책이 한 흐름으로 이어져 있기 때문에, 어느 레이어에서 인증이 끊기는지를 단계별로 확인해야 합니다. 저는 이 과정을 통해 개발 환경에서 동작하는 기능을 운영 환경으로 옮길 때는 코드만이 아니라 환경변수와 보안 정책까지 함께 배포 대상으로 봐야 한다는 점을 분명히 배웠습니다.

## Synology Docker 환경의 PostgreSQL 연결 안정화 트러블슈팅 면접 답변

실서비스 백엔드를 Synology Docker 환경에 배포하는 과정에서는 Spring Boot 애플리케이션이 PostgreSQL 연결 타임아웃으로 인해 반복적으로 불안정하게 재시작되는 문제가 있었습니다. 컨테이너는 떠 있는 것처럼 보이지만 실제 로그에는 `Connect timed out`, `Unable to determine Dialect without JDBC metadata`, `Application run failed` 같은 메시지가 반복됐고, 브라우저나 프록시 입장에서는 백엔드가 살아 있다가도 응답하지 않는 것처럼 보였습니다. 이 문제는 로그인이나 이미지 업로드 같은 개별 기능 이전에 서비스 전체 가용성을 떨어뜨리는 핵심 이슈였습니다.

처음에는 데이터베이스 설정값이 잘못된 것으로 의심했지만, 운영 환경의 `DATABASE_URL`, `DATABASE_USERNAME`, `DATABASE_PASSWORD`는 정상적으로 주입되고 있었습니다. 그래서 설정 오타보다는 실제 연결 경로에 문제가 있다고 보고, 컨테이너 상태와 네트워크 경로를 단계별로 다시 점검했습니다. PostgreSQL 컨테이너는 `healthy` 상태였지만, 백엔드 컨테이너가 데이터베이스에 붙는 시점에는 네트워크 또는 방화벽 영향으로 연결이 막히는 구간이 존재했고, 그 결과 HikariCP가 초기 연결을 만들지 못해 JPA 초기화 단계에서 애플리케이션 전체가 중단되고 있었습니다. 특히 Synology 환경에서는 컨테이너가 올라왔다는 사실과 애플리케이션이 실제 서비스 가능한 상태라는 사실을 분리해서 봐야 한다는 점이 중요했습니다.

해결은 시놀로지 방화벽과 컨테이너 간 접근 경로를 점검해 PostgreSQL 통신이 가능한 상태로 바꾸고, 백엔드가 실제로 데이터베이스 연결에 성공했는지를 로그 기준으로 재확인하는 방식으로 진행했습니다. 이후 HikariCP에서 `Added connection`, `Start completed`가 출력되고, JPA 초기화와 Tomcat 기동까지 이어지는 것을 확인했습니다. 여기서 저는 단순히 컨테이너가 `Up` 상태인지가 아니라, `Started WeddingApplication`까지 도달했는지를 배포 성공 기준으로 삼았습니다. 최종적으로는 PostgreSQL 연결이 안정화되면서 백엔드가 정상적으로 서비스 가능한 상태에 도달했고, 이후 상위 계층인 프록시나 OAuth 문제도 실제 애플리케이션 로직 관점에서 다시 볼 수 있게 됐습니다.

이 경험을 통해 운영 장애를 볼 때는 "프로세스가 떠 있는가"만 확인해서는 부족하고, 네트워크 연결 성공, 데이터베이스 풀 생성, ORM 초기화, HTTP 응답 가능 상태까지 계층별로 봐야 한다는 점을 다시 확인했습니다. 특히 Synology 같은 홈서버 계열 운영 환경에서는 방화벽과 Docker 네트워크 설정이 서비스 안정성에 직접 영향을 주기 때문에, 애플리케이션 코드와 인프라 설정을 같이 봐야 문제를 제대로 해결할 수 있다는 점을 배웠습니다.
