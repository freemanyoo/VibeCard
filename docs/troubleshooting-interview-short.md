# OpenClaw 이미지 생성 트러블슈팅 짧은 면접 답변

AI 청첩장 생성 기능을 구현하면서 OpenClaw를 통해 세 가지 모델 경로를 연동했는데, 그중 두 경로는 이미지 입력 payload 기대 형식이 달라 동일한 요청으로는 안정적으로 동작하지 않았습니다. 이 문제는 `/v1/files` 업로드는 정상인지, 이후 `/v1/chat/completions`와 `/v1/responses` 호출이 각각 어떤 응답을 주는지 직접 비교하고, OpenClaw 로그와 코드 경로를 함께 확인하면서 원인을 좁혔습니다. 그 결과 이미지 분석 경로를 `/v1/files` 업로드 후 `/v1/responses`에서 `input_image.source.type = "file_id"` 형식으로 통일했고, `/uploads/...`, 상대경로, 순수 파일명처럼 섞여 들어오던 이미지 참조도 하나의 실제 파일 경로로 정규화해 처리 안정성을 높였습니다.

추가로 이전 요청의 이미지 문맥이 다음 요청에 섞이는 문제를 막기 위해 요청마다 고유 `SessionKey`를 부여해 세션을 분리했고, 운영 환경에서만 발생하던 `405 Invalid HTTP method`는 Java HTTP 클라이언트를 `HTTP/1.1`로 고정하고 `Accept: application/json`을 명시하며 `Expect: 100-continue`를 비활성화해 해결했습니다. 또 Synology 내부에서는 Tailscale 공개 주소 대신 내부망 주소로 OpenClaw를 호출하도록 바꿔 네트워크 의존성을 줄였고, 그 결과 이미지 기반 AI 생성 흐름을 운영 환경에서도 일관되고 안정적으로 동작하도록 만들었습니다.

## Synology Docker 프록시 트러블슈팅 짧은 면접 답변

Synology Docker 환경에서 React 프론트와 Spring Boot 백엔드를 분리 배포했을 때, 브라우저의 `/api` 요청이 전부 `504 Gateway Timeout`으로 실패한 적이 있습니다. 처음에는 백엔드 로직 문제처럼 보였지만, 실제로는 프론트 Nginx가 `host.docker.internal:8086`으로 백엔드를 프록시하고 있었고, Synology 환경에서 이 우회 경로가 안정적으로 동작하지 않았던 것이 원인이었습니다. 백엔드 자체는 살아 있었지만 프론트 컨테이너 안에서 `curl http://host.docker.internal:8086`이 타임아웃 나는 것을 확인하면서 문제를 프록시 경로로 좁혔습니다.

해결은 프론트 Nginx 컨테이너를 백엔드와 같은 Docker 네트워크에 연결하고, 프록시 대상을 `host.docker.internal:8086`에서 `backend:8080`으로 바꾸는 방식으로 진행했습니다. 이후 컨테이너 내부에서 `backend` 서비스명으로 직접 통신이 가능해졌고, 외부 도메인 기준 `/api` 요청도 더 이상 `504`가 아니라 실제 백엔드 응답 코드로 바뀌었습니다. 추가로 운영 도메인을 Spring Security CORS 허용 목록에 반영해 `403` 문제도 정리했고, 결과적으로 Synology 운영 환경에서 프론트와 백엔드가 안정적으로 통신하는 구조를 만들었습니다.

## AI 청첩장 명령어 기반 입력 분리 및 폰트 정책 트러블슈팅 짧은 면접 답변

AI 청첩장 생성 기능에서 `명령어 기반`은 원래 텍스트만으로 디자인을 생성해야 했는데, 실제 구현을 확인해 보니 이미지 관련 값이 함께 전달될 수 있는 구조였습니다. 이 때문에 사용자는 텍스트 기반 결과를 기대하지만 실제 AI는 이미지 맥락까지 참고할 수 있었고, 결과 일관성이 흔들릴 수 있었습니다. 저는 프론트 요청 payload와 백엔드 처리 흐름을 같이 점검해, `명령어 기반`에서는 이미지 필드를 보내지 않도록 하고 서버에서도 방어적으로 이미지 입력을 무시하게 바꿨습니다. 이렇게 해서 텍스트 전용 생성 경로를 프론트와 서버 양쪽에서 확실히 분리했습니다.

또 하나는 폰트 정책 문제였습니다. `명령어 기반`에서도 AI가 폰트까지 정해야 했는데, 기존에는 `fontFamily`가 필수 응답이 아니어서 누락되거나 허용하지 않은 폰트가 들어올 수 있었습니다. 그래서 백엔드 프롬프트에 무료 폰트 목록을 직접 넣고 `fontFamily`를 필수값으로 요구했으며, 응답 파서에서는 허용 목록 검증과 fallback 로직을 추가했습니다. 배포 과정에서는 `.env.prod` 없이 컨테이너를 재기동해 포트 충돌과 일시적 `502`가 발생했지만, 운영 환경파일로 다시 올리고 frontend nginx를 reload해 바로 복구했습니다. 결과적으로 지금은 `명령어 기반`이 실제로 텍스트만 사용하고, 폰트도 AI가 무료 폰트 정책 안에서 직접 선택하는 구조로 안정화됐습니다.

## 운영 도메인 전환 후 Google OAuth 트러블슈팅 짧은 면접 답변

운영 도메인으로 서비스를 전환한 뒤 Google 로그인 버튼은 눌리지만 실제 로그인이 완료되지 않는 문제가 있었습니다. 프론트는 Google credential을 정상적으로 받고 있었기 때문에, 문제를 프론트 렌더링이 아니라 운영 환경의 인증 처리 단계로 좁혔습니다. 확인해 보니 시놀로지 운영 컨테이너에는 `GOOGLE_CLIENT_ID`가 비어 있었고, 운영 도메인 `https://vibecard.nextfreemanyoo.myds.me`도 Spring Security CORS 허용 목록에 빠져 있었습니다.

해결은 운영용 환경변수에 실제 `GOOGLE_CLIENT_ID`를 반영하고 백엔드를 재배포한 뒤, CORS 허용 목록에 운영 도메인을 추가하는 방식으로 진행했습니다. 이후 프론트에서 받은 Google credential이 백엔드에서 정상 검증되기 시작했고, 운영 환경에서도 Google 로그인이 정상적으로 완료됐습니다. 이 경험을 통해 OAuth는 프론트 SDK만이 아니라 운영 환경변수와 보안 정책까지 함께 맞아야 동작한다는 점을 확인했습니다.

## Synology Docker PostgreSQL 연결 안정화 짧은 면접 답변

실서비스 백엔드를 Synology Docker에 배포하는 과정에서는 PostgreSQL 연결 타임아웃 때문에 Spring Boot 애플리케이션이 반복적으로 불안정하게 재시작되는 문제가 있었습니다. 컨테이너는 떠 있는 것처럼 보였지만, 로그에는 `Connect timed out`와 `Unable to determine Dialect without JDBC metadata`가 반복돼 실제 서비스 가능 상태까지 도달하지 못하고 있었습니다. 저는 이 문제를 설정 오타보다 네트워크와 방화벽 문제로 보고, PostgreSQL 컨테이너 상태와 백엔드의 실제 연결 성공 여부를 분리해서 확인했습니다.

이후 시놀로지 방화벽과 컨테이너 간 접근 경로를 점검해 PostgreSQL 통신이 가능한 상태로 수정했고, HikariCP의 연결 생성과 JPA 초기화, Tomcat 기동 로그를 기준으로 배포 성공 여부를 다시 판단했습니다. 결과적으로 백엔드는 `Started WeddingApplication`까지 안정적으로 도달했고, 개별 기능 오류도 그 이후에 정상적으로 분리해서 볼 수 있게 됐습니다. 이 경험을 통해 운영 장애는 단순히 컨테이너 상태가 아니라 데이터베이스 연결과 애플리케이션 초기화 단계까지 함께 봐야 한다는 점을 배웠습니다.
