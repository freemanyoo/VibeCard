## 소셜 로그인 방식 고도화 (Google: Popup ID Token -> Redirect/Authorization Code 기반)

### 왜 해야 하나
- 운영 단계에서 인증 보안성과 감사 가능성을 높이기 위해서.
- 소셜 제공자(카카오/네이버/구글) 확장 시 공통 구조로 관리하기 위해서.
- 프론트 중심 토큰 처리 부담을 줄이고 서버 중심 검증/정책 통제를 강화하기 위해서.

### 현재 방식(팝업 + ID 토큰) 문제점
- OAuth 표준 코드 교환 흐름 대비 확장성이 낮음.
- 공급자별 예외 처리/정책이 프론트와 백엔드에 분산되기 쉬움.
- 계정 연동 정책(이메일 계정 <-> 소셜 계정) 관리가 복잡해짐.
- 환경(dev/stage/prod) 증가 시 인증 설정 추적과 운영 가시성이 떨어짐.

### 전환 시 장점 (Redirect/Authorization Code 기반)
- 표준 OAuth2 흐름으로 보안/운영 관점에서 안정적.
- 토큰 교환 및 검증을 서버에서 일원화 가능.
- 제공자 추가 시 아키텍처 재사용성이 높음.
- 감사 로그/이상 탐지/정책 적용 지점을 백엔드로 집중 가능.

### 전환 시 단점
- 구현 복잡도 증가 (리디렉션 URI, state/nonce, 에러 처리).
- 환경별 URI/콘솔 설정 관리 부담 증가.
- 초기 개발 속도는 현재 방식 대비 느림.

### 실행 기준 (언제 전환할지)
- 소셜 제공자 2개 이상 운영 시.
- 모바일/웹 동시 로그인 정책 통합 필요 시.
- 보안 감사/내부통제 요구가 생길 때.

### 작업 항목
- [ ] 인증 아키텍처 설계: Redirect + Authorization Code(+PKCE/서버 교환) 확정.
- [ ] 백엔드 콜백/토큰교환/계정연동 정책 구현.
- [ ] 프론트 로그인 UI를 리디렉션 흐름 기준으로 단순화.
- [ ] 운영 환경별 OAuth 설정 문서화(도메인, 리디렉션 URI, 비밀키 관리).
- [ ] 회귀 테스트: 기존 이메일 로그인/회원가입/권한 흐름 영향 점검.

## 현재 결정: 빠른 개발 우선 (JWT + Authorization 헤더 유지)

### 결정 이유
- 개발 속도 최우선: 구현/디버깅이 단순하고 변경 영향 범위가 작음.
- 기존 코드와 호환: 현재 `AuthProvider`, `axios interceptor` 구조를 크게 바꾸지 않아도 됨.
- 로컬 개발 편의: CORS + 쿠키(`withCredentials`, SameSite, Secure) 이슈를 당장 피할 수 있음.

### 현재 방식 장점
- 구현이 단순하고 학습 비용이 낮음.
- API 테스트(Postman/브라우저 네트워크)와 장애 추적이 쉬움.
- 프론트/백엔드 독립 개발이 비교적 쉬움.

### 현재 방식 문제점/리스크
- 토큰이 `localStorage`에 있어 XSS 발생 시 탈취 위험이 있음.
- 토큰 폐기/강제 로그아웃을 서버에서 즉시 통제하기 어려움(만료 전까지 유효).
- 브라우저 확장/공용PC 환경에서 세션 잔존 리스크가 커짐.
- 장기적으로 소셜 제공자 확장 시 인증 정책 일관성 유지가 어려워질 수 있음.

### 쿠키 기반(HttpOnly) 전환 시 장점
- JS에서 토큰 접근 불가(`HttpOnly`)라 XSS 탈취 위험 감소.
- 인증 수명/폐기/보안정책을 서버 중심으로 통제하기 쉬움.
- 운영/감사 관점에서 인증 흐름 관리가 수월함.

### 쿠키 기반(HttpOnly) 전환 시 단점
- CORS/쿠키 속성(SameSite, Secure, Domain) 설정 복잡도 증가.
- CSRF 대응(토큰 또는 Origin 검증) 추가 구현 필요.
- 초기 전환 시 테스트 케이스 및 장애 지점이 증가.

### 빠른 개발 유지 시 필수 보완 항목 (단기)
- [ ] 로그인/회원가입 화면에 에러 메시지 유지(자동 리다이렉트로 메시지 유실 금지).
- [ ] `auth/*` 요청별 토큰 첨부 정책 고정(예: `/auth/me`는 첨부, 공개 엔드포인트는 미첨부).
- [ ] CSP/XSS 방어 점검(입력 렌더링 지점, `dangerouslySetInnerHTML` 사용 금지 확인).
- [ ] 액세스 토큰 만료 시간 단축 + 재로그인 UX 정리.
- [ ] 로그아웃 시 로컬 저장소 완전 삭제 및 보호 페이지 접근 차단 재검증.

### 전환 트리거 (이 조건이면 쿠키 기반 전환 시작)
- [ ] 운영 배포 직전(프로덕션 도메인 연결 시점).
- [ ] 소셜 로그인 제공자 2개 이상 도입 시.
- [ ] 보안 점검/감사 요구사항이 생긴 경우.

## AI 생성 기능 전반 운영 안정화

### 왜 해야 하나
- 현재 AI 기능은 스킨 제작, 청첩장 생성(이미지 기반), 청첩장 생성(명령어 기반)으로 확장되고 있어 공통 운영 기준이 필요함.
- AI 호출은 OpenClaw/OpenAI 계열 외부 모델에 의존하므로, 입력 검증/오류 처리/추적성을 공통 정책으로 묶어야 함.
- 특정 기능만 따로 보강하면 이후 AI 기능이 늘어날 때 동일한 문제가 반복됨.

### 현재 구현 상태
- 스킨 제작: `/api/admin/skins/ai-generate`로 AI 스킨 설정 생성.
- 청첩장 생성(이미지 기반): `/api/invitations/ai-generate-from-image`로 업로드 이미지 분석 후 `configPatch` 반영.
- 청첩장 생성(명령어 기반): 현재 프론트 초안 생성 중심이며, 향후 AI 호출 확장 예정.
- 각 기능이 서로 다른 입력값/응답 구조를 가지지만, 공통 검증과 에러 처리 정책은 아직 분산된 상태.

### 현재 문제점
- 기능별 입력 검증 수준이 다름: `photoUrl`, `imageStyle`, 프롬프트, 모델 선택값, 로컬 목적값 검증을 공통 기준으로 묶지 못함.
- 외부 에러 응답에 내부 원인(업스트림 호출 실패, 설정값 문제, 경로 문제)이 그대로 노출될 수 있음.
- AI 호출 타임아웃/재시도/실패 분류(4xx vs 5xx)가 기능별로 일관되지 않음.
- 요청 단위 추적 ID가 없어 스킨 생성 ↔ 청첩장 생성 ↔ 업스트림 AI 호출 흐름 추적이 불편함.
- 기능별 응답 스키마(`config`, `meta`, `configPatch`, 분석문, 축하문 등) 검증/기본값 병합 규칙이 분산돼 있음.
- 프롬프트 차단/보안 필터링은 스킨 제작 중심으로 들어가 있고, 다른 AI 기능에는 아직 공통화가 덜 됨.

### 작업 항목
- [ ] AI 기능 공통 입력 검증 정책 수립: `photoUrl`, `imageStyle`, 프롬프트, 모델 alias, 로컬 목적값(enum/화이트리스트) 검증 공통화.
- [ ] `photoUrl` 입력 검증 강화: `/uploads/...` 또는 `file_...`만 허용, `..`/절대경로 차단, 이미지 확장자 화이트리스트 적용.
- [ ] `imageStyle`를 `standard|full` enum으로 엄격 검증하고, 잘못된 값은 400으로 즉시 실패 처리.
- [ ] AI 프롬프트 보안 필터링을 스킨 생성뿐 아니라 명령어 기반 청첩장 생성에도 공통 적용.
- [ ] 외부 응답 에러 문구를 기능별 일반화(`AI 생성 실패`)하고, 내부 상세 원인은 서버 로그로만 남기기.
- [ ] OpenClaw/OpenAI 계열 호출 타임아웃을 20~30초 기준으로 통일하고, 5xx에 한해 1회 재시도 정책 적용.
- [ ] 요청 단위 `requestId`를 생성해 Controller/Service/OpenClaw 호출 로그를 연결.
- [ ] 기능별 응답 스키마 검증 및 기본값 병합 규칙 정리: `config`, `meta`, `configPatch`, 분석문, 축하문 공통 처리 기준 마련.
- [ ] AI 호출 클라이언트 추상화: 스킨 제작/청첩장 생성이 같은 인증/엔드포인트/로깅 정책을 재사용하도록 서비스 계층 정리.
- [ ] 성공/실패 `curl` 테스트 예시와 운영 점검 절차를 기능별로 문서화.

## PostgreSQL + MinIO 전환 설계

### 왜 해야 하나
- 현재 로컬 파일 업로드(`/uploads`) 중심 구조는 단일 서버 개발에는 빠르지만, 배포 환경에서는 파일 경로/서버 분리/확장성 문제가 생김.
- 이미지 기능이 메인 사진, 갤러리, 썸네일, AI 분석용 파생본까지 확장되고 있어 파일 저장과 메타데이터 저장을 분리하는 구조가 필요함.
- AI 이미지 분석은 원본이 아니라 분석용 경량 파생본을 별도로 관리하는 편이 안정적이고 빠름.

### 권장 역할 분리
- `PostgreSQL`: 사용자, 청첩장 데이터, 이미지 메타데이터, AI 생성 이력 저장
- `MinIO`: 원본 이미지, 썸네일, AI 분석용 파생 이미지 저장

### 현재 구조의 한계
- 업로드 파일이 애플리케이션 서버 로컬 디스크에 묶여 있음.
- 서버를 분리하거나 여러 대로 늘리면 파일 경로 일관성이 깨질 수 있음.
- AI 분석 시 어떤 파일을 어떤 방식으로 전달할지(원본/썸네일/분석본) 경계가 불명확함.
- 백업/이관/스토리지 확장 시 운영 부담이 커짐.

### 목표 구조
- 업로드 시 원본 파일 저장
- 동시에 썸네일/AI 분석용 리사이즈본 생성
- 실제 파일은 MinIO에 저장
- PostgreSQL에는 파일 키, URL, 크기, MIME, 사용자/청첩장 연결 정보만 저장
- AI 호출은 분석용 이미지(`analysis`) 기준으로 수행

### 작업 항목
- [ ] `PostgreSQL + MinIO` 기준 최종 저장 구조 확정 (로컬 개발/운영 공통 정책 포함).
- [ ] 이미지 메타데이터 테이블 설계 (`original`, `thumb`, `analysis` 경로/URL, 크기, MIME, 소유자, 연결 엔티티).
- [ ] AI 생성 이력 테이블 설계 (`source_image_id`, 타입, provider, 결과 요약, `configPatch`, 생성 시각).
- [ ] 업로드 파이프라인 설계: 원본 저장 후 썸네일/분석용 파생본 생성.
- [ ] Spring Boot에서 MinIO(S3 호환) 업로드/조회 클라이언트 도입.
- [ ] 현재 `/uploads` 의존 로직을 스토리지 추상화 계층으로 이동.
- [ ] AI 호출이 원본이 아닌 분석용 이미지(`analysis`)를 사용하도록 구조 변경.
- [ ] 로컬 개발용 `docker compose` 초안 작성 (PostgreSQL + MinIO + 앱).
- [ ] 향후 S3/R2 등 외부 오브젝트 스토리지로 이전 가능한 키 구조/버킷 규칙 문서화.
